# Bounded Evidence Auto-Repair Design

## Goal

Make independent visual evidence capture converge safely. Evidence may diagnose why an acceptance run failed, but it must not repair the product or rewrite acceptance tests inside the Evidence turn. Product and acceptance-harness defects return to a bounded Repair loop; environment failures remain bounded Evidence retries.

## Problem

The current Agent evidence operation returns only media paths. When Codex cannot capture valid media, it has no structured way to distinguish a product defect, a broken acceptance test, and an unavailable environment. Its prompt also permits code changes when acceptance exposes a defect, and the Agent turn has no wall-clock limit. With unrestricted host execution, a single Evidence turn can therefore edit E2E tests, relaunch Electron repeatedly, and continue indefinitely. The Runtime's retry limit does not help until that Agent turn returns.

## Decision

Introduce a structured Evidence outcome and move all corrective work back through the Runtime state machine.

An Evidence turn returns exactly one of:

```ts
type EvidenceCaptureResult =
  | {
      outcome: "CAPTURED";
      evidence: RepairEvidencePath[];
    }
  | {
      outcome: "PRODUCT_DEFECT" | "ACCEPTANCE_DEFECT";
      diagnosis: string;
      code?: "EVIDENCE_WORKSPACE_MUTATION";
      failedCommand?: string;
      errorSummary?: string;
    }
  | {
      outcome: "ENVIRONMENT_FAILURE";
      diagnosis: string;
      code:
        | "EVIDENCE_TARGET_UNREACHABLE"
        | "EVIDENCE_CAPTURE_PERMISSION_DENIED"
        | "EVIDENCE_CAPTURE_PROCESS_FAILED"
        | "EVIDENCE_CAPTURE_TIMEOUT";
      failedCommand?: string;
      errorSummary?: string;
    };
```

`CAPTURED` requires at least one screenshot or recording. Defect and environment outcomes must not contain evidence. `diagnosis` and `errorSummary` are trimmed and limited to 4,000 characters; `failedCommand` is trimmed and limited to 2,000 characters. Timeout and workspace-mutation codes are generated by the adapter, not selected freely by the model.

Only Evidence retains `danger-full-access` with network enabled. Assessment remains read-only with network disabled, and Repair remains workspace-write with network disabled.

## Evidence Turn Boundary

The Evidence prompt must:

- tell Codex to run the existing acceptance target and capture real media;
- prohibit changes to product files, test files, configuration, dependencies, generated bundles, and Git state;
- prohibit weakening or rewriting the acceptance criteria;
- require a defect outcome instead of a repair when the observed product behavior is wrong;
- require an acceptance-defect outcome when the verifier or fixture is wrong;
- require an environment-failure outcome for startup, port, permission, dependency, or infrastructure failures;
- require acceptance processes to run in the foreground and be stopped before returning.

The adapter enforces a five-minute wall-clock limit for the complete Evidence turn, including inspection, service startup, interaction, capture, and structured response generation. Repair time is not included.

The adapter watches Codex file-change events. A change outside the prepared Evidence intake directory aborts the turn and produces an `ACCEPTANCE_DEFECT` diagnosis with code `EVIDENCE_WORKSPACE_MUTATION`. Media written below the intake directory is allowed. The aborted turn cannot supply acceptable evidence.

Each Evidence turn receives a unique private temporary directory through the Codex process environment. The prompt requires Electron acceptance launches to use a user-data directory below that location and requires application runtime data to be isolated there when the project supports an override. This prevents the acceptance instance from sharing the running desktop application's profile or Runtime database.

On timeout or cancellation caused by the Evidence policy, the adapter aborts the SDK turn, disposes the thread handle, and removes the private temporary directory after the turn settles. Acceptance commands must not daemonize or deliberately detach child processes; the SDK abort signal is the process-cleanup boundary for arbitrary Agent commands.

## Runtime State Flow

### Successful capture

```text
EVIDENCE_CAPTURE
  -> CAPTURED
  -> import media
  -> EVIDENCE_CHECK
  -> ACCEPTANCE_REVIEW when reviewable
```

The existing evidence import, path containment, media inspection, and human acceptance behavior remain unchanged.

### Product or acceptance defect

```text
EVIDENCE_CAPTURE
  -> PRODUCT_DEFECT or ACCEPTANCE_DEFECT
  -> record diagnosis event
  -> REPAIRING with pending REPAIR
  -> repair completes
  -> EVIDENCE_CAPTURE again
```

The transition starts a new Repair iteration and:

- increments `repair.automaticRepairRetries`;
- resets `repair.evidenceRetries` to zero;
- stores the diagnosis and command summary as Repair feedback;
- removes stale `repair.delivery` and `repair.deliveryDraft` values;
- preserves the approved Assessment and Agent session.

Repair may change product code or acceptance tests according to the diagnosis. An acceptance-test repair does not prove the product change by itself; the next independent Evidence turn must still run the real application and capture valid visual evidence.

Automatic Evidence-triggered Repair is capped at five transitions per continuous automatic loop. `automaticRepairRetries` is separate from the normal Repair `iteration`, so older Issues do not lose their automatic budget merely because a user previously requested Repair. A successful Evidence capture ends the loop. A user-initiated Retry Repair starts a new manual attempt and resets the automatic-loop counter.

If a sixth defect outcome would be required, Runtime transitions to `REPAIR_FAILED` with `AUTOMATIC_REPAIR_LIMIT_REACHED`, preserves the latest diagnosis for the user, and queues nothing. The existing manual Retry Repair action remains available.

### Environment failure

```text
EVIDENCE_CAPTURE
  -> ENVIRONMENT_FAILURE or five-minute timeout
  -> EVIDENCE_CAPTURE retry, at most two automatic retries
  -> EVIDENCE_FAILED when exhausted
```

Environment failures do not increment the Repair iteration or `automaticRepairRetries`. They use the existing `repair.evidenceRetries` budget. A timeout has the stable code `EVIDENCE_CAPTURE_TIMEOUT`. Existing evidence import and inspection failures also continue to use the Evidence retry budget.

Runtime interruption remains special: `RUNTIME_STOPPING` requeues the same operation without consuming either counter.

## Events and User Visibility

Runtime records distinct events for:

- `EVIDENCE_PRODUCT_DEFECT_DETECTED`;
- `EVIDENCE_ACCEPTANCE_DEFECT_DETECTED`;
- `EVIDENCE_ENVIRONMENT_FAILURE`;
- `EVIDENCE_CAPTURE_TIMED_OUT`;
- `EVIDENCE_AUTOMATIC_REPAIR_QUEUED`;
- `AUTOMATIC_REPAIR_LIMIT_REACHED`.

Events contain safe, bounded diagnosis text, failure code, command summary when supplied, Repair iteration, and both retry counters. They must not expose absolute private paths or raw environment output.

The existing activity stream may continue to show Agent commands. Issue status is the authoritative UI signal:

- `EVIDENCE_CAPTURE` means the application is being exercised and media is being captured;
- `REPAIRING` after a defect event means acceptance found a defect and automatic Repair is running;
- `EVIDENCE_FAILED` means capture infrastructure or media verification exhausted its retry budget;
- `REPAIR_FAILED` with `AUTOMATIC_REPAIR_LIMIT_REACHED` means the automatic fix loop exhausted five rounds.

No new user action is required for automatic transitions.

## Persistence and Compatibility

Add optional `repair.automaticRepairRetries` to the Issue schema. The default is zero, so existing SQLite rows remain valid without a migration. Existing `automaticEvidenceRetries` data remains readable for backward compatibility but is not reused for the new Repair-loop budget.

The Runtime store continues to persist the complete Issue JSON and pending operation atomically with its event. Recovery derives `REPAIR` from `REPAIRING` and `CAPTURE_EVIDENCE` from `EVIDENCE_CAPTURE` as it does today.

## Error Handling

- Invalid or contradictory structured output is an Evidence process failure and consumes the Evidence retry budget.
- A `CAPTURED` result with no media is invalid.
- A defect result cannot be accepted as evidence, even if files exist in the intake directory.
- Workspace mutation aborts Evidence immediately and routes the diagnosis to Repair; the next Repair owns validation, correction, or reversion of that mutation.
- Environment failure never grants authority to edit the product.
- Repair failures retain the existing `REPAIR_FAILED` behavior.
- Evidence retry exhaustion preserves the latest completed implementation state and failure diagnosis.

## Testing

### Core

- Parse every valid Evidence outcome and reject mixed or incomplete outcomes.
- Transition product and acceptance defects from Evidence to a new Repair iteration.
- Keep environment and automatic-Repair counters independent.
- Stop the sixth automatic defect at `REPAIR_FAILED`.
- Reset the automatic-loop counter on a manual Retry Repair.
- Preserve existing Issue JSON compatibility.

### Codex adapter

- Require the strict Evidence output union.
- Verify the prompt prohibits source, test, dependency, and Git changes.
- Permit media writes below the intake directory.
- Abort on a file change outside that directory and return the workspace-mutation diagnosis.
- Abort at five minutes and report `EVIDENCE_CAPTURE_TIMEOUT`.
- Keep Assessment and Repair permission options unchanged.
- Provide and clean a unique private Evidence temporary directory.

### Runtime worker

- Route `PRODUCT_DEFECT` and `ACCEPTANCE_DEFECT` to pending `REPAIR` with diagnostic feedback.
- Route `ENVIRONMENT_FAILURE` to bounded pending `CAPTURE_EVIDENCE`.
- Reset Evidence retries after an automatic Repair transition.
- Preserve counters across restart without charging an interrupted turn.
- Preserve current import, inspection, and retry-limit behavior for successful media paths.

### Acceptance

Add an end-to-end Runtime test for:

```text
Repair completes
  -> first Evidence reports PRODUCT_DEFECT
  -> automatic Repair completes
  -> second Evidence captures reviewable media
  -> ACCEPTANCE_REVIEW
```

Add controlled cleanup coverage proving that a foreground acceptance process is canceled on success, failure, and timeout, and that its private temporary directory is removed.

## Non-goals

- Letting Evidence modify product or acceptance files directly.
- Treating a passing rewritten test as visual proof.
- Adding a host-managed browser broker.
- Removing unrestricted host execution from Evidence.
- Automatically repairing environment or operating-system permission failures.
- Guaranteeing cleanup of processes that deliberately daemonize or escape the Codex SDK process boundary.
